Quero que você atue como um **arquiteto de software sênior, especialista em sistemas web, segurança da informação, gestão agropecuária, bancos de dados e integração entre sistemas**.

Sua tarefa é desenvolver um **sistema web completo para gestão de fazendas de gado**, com foco em:

- Segurança
- Facilidade de uso
- Confiabilidade
- Escalabilidade
- Rastreabilidade das informações
- Facilidade de manutenção
- Integração com outros sistemas
- Geração de relatórios
- Geração de tabelas e consultas personalizadas

O sistema deverá ser desenvolvido com arquitetura profissional, pensando desde o início em um sistema que possa crescer para atender várias fazendas, usuários e grandes volumes de dados.

# 1. OBJETIVO DO SISTEMA

O sistema deverá permitir o gerenciamento completo de propriedades rurais voltadas à criação de gado.

A ideia é centralizar as informações da fazenda em um único sistema, permitindo controlar animais, lotes, pastagens, alimentação, pesagens, reprodução, movimentações, estoque, custos, usuários, relatórios, contas a receber, contas a pagar e demais informações necessárias para a gestão da propriedade.

O sistema deverá funcionar via navegador, sendo responsivo para:

- Computadores
- Notebooks
- Tablets
- Celulares

A interface deverá ser simples e intuitiva, permitindo que usuários com pouca experiência em informática consigam utilizar o sistema.

A segurança é uma das prioridades máximas do projeto.

Implemente o sistema seguindo boas práticas modernas de segurança e, quando aplicável, as recomendações do OWASP.

O sistema deverá possuir:

### Autenticação

- Login seguro
- Senhas armazenadas utilizando hash forte
- Nunca armazenar senha em texto puro
- Controle de sessão
- Expiração de sessão
- Logout seguro
- Proteção contra brute force
- Rate limiting
- Recuperação de senha segura
- Possibilidade de autenticação em dois fatores (2FA)
- Controle de dispositivos/sessões ativas

### Autorização

Criar um sistema robusto de permissões.

Exemplo:

Administrador

Veterinário
Zootecnista
Funcionário
Operador
Visualização

As permissões devem poder ser configuradas por:

- Módulo
- Tela
- Operação

- Visualizar
- Editar
- Excluir
- Exportar
- Imprimir
- Importar

Não confiar apenas nas restrições do frontend.

Toda autorização deverá ser validada também no backend.

### Proteções

Implementar proteção contra:

- SQL Injection
- XSS
- CSRF
- Brute Force
- Session Hijacking
- IDOR
- Upload de arquivos maliciosos
- Manipulação de parâmetros
- Escalada de privilégios
- Mass Assignment
- Vazamento de informações
- Enumeração de usuários
- Ataques de força bruta
- Replay de requisições quando aplicável

Utilizar:

- HTTPS
- Headers de segurança
- Cookies seguros quando utilizados
- CORS corretamente configurado
- CSP quando aplicável
- Rate limiting
- Validação de entrada
- Sanitização
- Prepared Statements/ORM seguro
- Gestão segura de secrets

Nunca deixar:

- Senhas
- Tokens
- Chaves de API
- Credenciais do banco
- Secrets

diretamente no código-fonte.

Utilizar variáveis de ambiente e/ou gerenciamento apropriado de secrets.

| 000124 | 20/10/2026 | 08:33 | 412 | OK |

- Casas decimais
- Máscara
- Opções disponíveis
- Ordem de exibição
- Se aparece em consultas
- Se aparece em relatórios
- Se pode ser utilizado como filtro
- Se pode ser utilizado em ordenação
- Se pode ser utilizado em agrupamento

## 40.2 Tipos de campos

Suportar pelo menos:

- Texto
- Texto longo
- Número inteiro
- Número decimal
- Data
- Data e hora
- Hora
- Sim/Não
- Lista de opções
- Lista múltipla
- Valor monetário
- Percentual
- E-mail
- Telefone
- CPF/CNPJ
- Campo de referência para outro cadastro

Exemplo:

Campo:

`Categoria genética`

Tipo:

`Lista`

Opções:

- Nelore PO
- Nelore LA
- Angus
- Brangus
- Cruzado

---

## 40.3 Campos condicionais

Quando fizer sentido, permitir campos condicionais.

Exemplo:

Se:

`Sexo = Fêmea`

mostrar:

- Data do primeiro cio
- Número de partos
- Data do último parto
- Situação reprodutiva

Se:

`Sexo = Macho`

mostrar:

- Data da entrada em reprodução
- Exame andrológico
- Situação reprodutiva

---

## 40.4 Cadastros personalizados

A arquitetura deverá permitir futuramente a criação de novos tipos de cadastro sem necessidade de desenvolver uma tela completamente nova do zero.

Exemplo:

O administrador poderá criar um cadastro chamado:

**Equipamentos**

Campos:

- Código
- Descrição
- Marca
- Modelo
- Número de série
- Data de aquisição
- Valor
- Localização
- Status

Outro exemplo:

**Implementos agrícolas**

Campos:

- Código
- Descrição
- Fabricante
- Modelo
- Ano
- Horímetro
- Status
- Observações

Esses cadastros deverão poder participar, quando configurado, de:

- Relatórios
- Tabelas
- Filtros
- Consultas
- Exportações
- Auditoria

---

## 40.5 Gerador de telas

Sempre que possível, utilizar uma arquitetura orientada a metadados para que os formulários sejam construídos dinamicamente a partir da configuração dos campos.

Por exemplo:

```text
Cadastro: Animal

Campo              Tipo          Obrigatório
------------------------------------------------
Brinco              Texto         SIM
Sexo                Lista         SIM
Raça                Lista         SIM
Nascimento          Data          SIM
Peso                Decimal       NÃO
Lote                Referência    NÃO
SISBOV              Texto         NÃO
Observação          Texto longo   NÃO
```

O sistema deverá gerar automaticamente o formulário correspondente.

---

## 40.6 Segurança

Campos e cadastros configuráveis NÃO podem permitir que um administrador comum execute código arbitrário, SQL ou scripts no servidor.

Nunca permitir:

- SQL livre
- JavaScript livre
- HTML executável
- Scripts
- Comandos do sistema operacional

As configurações deverão utilizar estruturas controladas pelo sistema.

---

## 40.7 Banco de dados

Antes de implementar esse mecanismo, analisar cuidadosamente a melhor estratégia.

Comparar, quando aplicável:

- Colunas tradicionais
- Tabelas de atributos
- EAV
- JSON/JSONB
- Metadados + estrutura híbrida

Escolher a solução que ofereça o melhor equilíbrio entre:

- Segurança
- Performance
- Flexibilidade
- Integridade
- Consultas
- Relatórios
- Indexação
- Manutenção

Não utilizar EAV automaticamente apenas por ser flexível.

Justificar tecnicamente a escolha.

---

## 40.8 Integração com o gerador de relatórios

Campos personalizados deverão poder ser utilizados no gerador de relatórios.

Exemplo:

O administrador criou:

`Peso ao desmame`

Esse campo deverá poder aparecer em:

- Relatório
- Tabela personalizada
- Filtro
- Ordenação
- Agrupamento
- Exportação

---

## 40.9 Integração com o gerador de tabelas

Campos personalizados também deverão aparecer automaticamente como opções no gerador de tabelas.

Exemplo:

Fonte:

`Animais`

Campos disponíveis:

- Brinco
- Raça
- Sexo
- Peso
- Lote
- Pasto
- Peso ao desmame
- Classificação genética

O usuário poderá montar sua própria tabela.

---

## 40.10 Controle de alterações

Alterações na estrutura dos campos deverão ser auditadas.

Registrar:

- Usuário
- Data
- Hora
- Campo criado
- Campo alterado
- Configuração anterior
- Nova configuração

Não permitir que alterações estruturais apaguem silenciosamente dados já cadastrados.

Por exemplo:

Se o administrador criar:

`Número do SISBOV`

e posteriormente desativar o campo, os dados históricos deverão permanecer preservados.

---

## 40.11 Ativação e desativação

Os campos deverão possuir status:

- Ativo
- Inativo

Ao desativar um campo:

- Não mostrar nos novos formulários
- Não permitir novos lançamentos
- Preservar os dados existentes
- Continuar permitindo consulta histórica
- Manter os dados disponíveis para auditoria e relatórios, conforme permissões

---

## 40.12 Permissões

Campos sensíveis poderão possuir controle de acesso.

Exemplo:

O campo:

`Valor de compra`

poderá ser visualizado apenas por:

- Administrador
- Gerente

Enquanto um funcionário comum poderá visualizar os demais dados do animal sem visualizar esse valor.

Portanto, considerar permissões também em nível de campo quando tecnicamente justificável.

---

## 40.13 Princípio arquitetural

A funcionalidade de campos e cadastros configuráveis deverá ser planejada desde o início da arquitetura.

Não implementar como um recurso improvisado posteriormente.

A solução deverá ser compatível com:

- Gerador de relatórios
- Gerador de tabelas
- API
- Importação
- Exportação
- Auditoria
- Multi-fazenda
- Controle de permissões
- Aplicativo mobile futuro

Antes de implementar, apresentar a arquitetura escolhida e explicar como os campos configuráveis serão armazenados, validados, consultados, indexados, auditados e disponibilizados pela API.
